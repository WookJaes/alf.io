# Git 규칙

브랜치·커밋·PR 작업에 적용한다. 사용자 요청과 기존 작업 상태를 우선하며 커밋·푸시·이력 변경은 명시적인 승인 범위에서 수행한다.

## 브랜치

- 현재 기본 브랜치는 `main`이다. 새 작업은 최신 원격 기본 브랜치를 확인해 분기하고, 병합할 때는 PR을 사용한다. 기본 브랜치가 바뀌면 이 규칙도 갱신한다.
- 이름: `<타입>/<이슈번호>-<영문-요약>`. 대응 이슈가 없으면 번호를 생략한다.
- 예: `feat/42-reservation-quantity`, `docs/git-conventions`.
- 이슈 번호에 앞자리 0을 붙이지 않는다. 요약은 소문자 영문 kebab-case로 쓰며 개인 이름·날짜는 넣지 않는다.
- 진행 중인 작업의 브랜치는 사용자 요청에 따라 이어서 사용한다.

| 타입 | 용도 |
|---|---|
| feat | 기능 추가 |
| fix | 버그 수정 |
| docs | 문서 변경 |
| test | 테스트 추가·수정 |
| refactor | 동작 변경 없는 구조 개선 |
| chore | 빌드·설정·하네스 등 |

## 커밋

- Conventional Commits: `<타입>: <한국어 요약>`. 제목은 50자 이내로 작성한다.
- 예: `chore: 프로젝트 작업 절차 추가`, `docs: Git 규칙 작성`.
- 하나의 커밋은 하나의 논리적 변경으로 구성한다. 기능과 해당 회귀 테스트처럼 함께 검토해야 하는 파일은 같이 묶는다.
- 요청 범위의 파일만 명시적으로 스테이징하고 `git diff --cached`와 `git diff --cached --check`로 내용을 확인한다. 기존 스테이징·미커밋 변경을 임의로 제거하지 않는다.
- 제품 작업 자료, 실험 기록, 원본 로그는 이번 커밋의 목적에 포함되는 경우에만 선택한다.
- 제목의 이슈 번호는 생략하고 PR에서 연결한다. 기존 커밋의 수정·재작성은 별도 요청이 있을 때 수행한다.

## PR과 검증

- 제목: `<타입>: <한국어 요약> (#이슈번호)`. 대응 이슈가 없으면 번호를 생략한다.
- 본문은 문제와 변경된 동작, 실제 검증 결과, 미검증 범위를 간단히 적는다. [PR 템플릿](https://github.com/WookJaes/alf.io/blob/main/.github/PULL_REQUEST_TEMPLATE.md)을 따른다.
- 이슈를 완전히 해결하면 `Closes #번호`, 일부만 해결하면 `Refs #번호`로 연결한다. 다른 저장소의 이슈는 저장소 이름까지 명시한다.
- 코드 변경은 영향 범위에 맞는 검증을 수행하고 문서 변경은 링크·내용·diff를 확인한다. PostgreSQL 통합 테스트에는 Docker가 필요하며 컴파일 성공과 실제 테스트 통과를 구분한다.
- 병합 방식·보호 규칙·CI 조건은 대상 저장소의 실제 설정과 사용자 지시에 따른다.
