# 명단 비교 비서 — 사람이 직접 하는 평가 안내

> 2026-10-16 안내: 기존 사용자 수동 처리 471초·Codex 에이전트 비서 사용 204.15초는 이미 수행한 참고 측정입니다. 결과와 조건 차이는 [대표 평가 문서](attendee-assistant-evaluation.md#기존-수동-처리에이전트-사용-참고-측정)에 정리했습니다. 이 문서는 향후 별도 평가를 위한 절차이며 이슈 #37에서 새 비교 평가나 유료 호출을 요구하지 않습니다. 아래 절차의 조건을 과거 측정에 소급 적용하지 않습니다.

**같은 명단을 두 방식으로 처리하고, 걸린 시간과 결과를 비교합니다.**

> 준비 → ① 직접 처리하며 시간 재기 → ② 비서로 처리하며 시간 재기 → ③ 결과표 채우기

준비 중에는 시간을 재지 않습니다. 수동 처리와 비서 사용을 **둘 다** 측정해야 합니다.

## 먼저 준비하기 — 시간 측정 없음

### A. 로컬 관리자 화면 열기

1. Docker Desktop과 로컬 PostgreSQL을 실행합니다.
2. API 키 환경변수를 설정한 **같은 터미널**의 프로젝트 루트에서 실행합니다.

```zsh
./gradlew -Pprofile=dev :bootRun
```

3. [관리자 화면](http://localhost:8080/admin)에 로그인합니다.

서버를 아직 설정하지 않았다면 [로컬 설정 안내](attendee-reconciliation.md#로컬-설정과-실행-순서)를 먼저 따릅니다. 기존 암호화 키는 재사용합니다. 기본 DB 준비는 [개발 실행 안내](../README.md#run-in-development-mode)를 참고합니다.

### B. 비교할 파일 두 개 준비하기

실제 참석자 정보가 없는 **로컬 평가용 행사**에서 티켓 3장을 예약·발급합니다. 가능하면 한 예약에서 3장을 발급하고, 각 티켓의 참석자 이메일을 아래처럼 설정합니다.

| 티켓 구분 | 참석자 이메일 |
|---|---|
| A | `a@example.invalid` |
| B | `b@example.invalid` |
| C | `c@example.invalid` |

세 티켓 모두 시스템 비교 대상 상태인 `ACQUIRED`, `CHECKED_IN`, `TO_BE_PAID` 중 하나여야 합니다. 판매 가능한 미발급 티켓은 비교 대상이 아닙니다.

행사 화면에서 참석자를 **CSV로 내보내고 `ID`, `E-Mail`을 선택**합니다. `Reservation E-Mail`이 아닌 참석자 `E-Mail`입니다. 티켓이 정확히 3행이고 ID가 서로 다른지 확인한 뒤 `system.csv`로 보관합니다.

`system.csv`를 복사해 `input.csv`를 만들고 아래처럼 편집합니다.

| 편집 순서 | `input.csv`에서 할 일 |
|---|---|
| 1 | A 행은 그대로 둡니다. |
| 2 | B 행은 그대로 둡니다. |
| 3 | B 행을 복제하고, 복제한 행의 이메일을 `different@example.invalid`로 바꿉니다. |
| 4 | C 행을 삭제합니다. |
| 5 | 시스템에 없는 새 UUID와 `unknown@example.invalid`로 행을 추가합니다. |

새 UUID는 아래 명령으로 만듭니다. A·B의 ID는 내보낸 UUID를 그대로 사용합니다.

```zsh
python3 -c 'import uuid; print(uuid.uuid4())'
```

**준비 완료 확인**

- [ ] `system.csv`: 헤더 + 티켓 3행
- [ ] `input.csv`: 헤더 + 데이터 4행, UTF-8 CSV
- [ ] 두 파일을 별도로 보관했고 평가 중 시스템 정보를 변경하지 않음
- [ ] 스톱워치와 아래 결과표를 준비함

## ① 수동 처리 — 직접 대조하기

**시작:** 두 파일을 열기 직전에 스톱워치를 시작합니다.

1. `system.csv`와 `input.csv`를 엽니다.
2. 티켓 ID별로 정상·누락·중복·이메일 불일치를 기록합니다.
3. 판단 근거인 CSV 레코드 번호와 시스템 값을 적습니다.
4. 확인 필요 항목마다 안내문을 작성합니다.
5. 판정과 안내문을 검토·수정한 뒤, 최종 안내문을 복사해 결과 메모에 붙여 넣습니다.

**종료:** 모든 판정·근거와 안내문을 확정해 복사했을 때 멈춥니다. 시간과 수정 횟수를 결과표에 적습니다.

## ② 비서 사용 — 화면에서 처리하기

해당 행사의 **명단 비교** 메뉴를 엽니다. 수동 처리 결과는 보지 않습니다.

**시작:** CSV 파일을 선택하기 직전에 스톱워치를 시작합니다.

1. `input.csv`를 선택하고 비교를 실행합니다.
2. 판정과 CSV·시스템 근거를 검토합니다.
3. 확인 필요 항목 3개를 선택하고 **설명·초안 생성**을 누릅니다.
4. 설명과 초안을 읽고, 필요한 문구를 수정합니다.
5. 확정한 초안 3개를 복사해 결과 메모에 붙여 넣습니다.

**종료:** 모든 결과 검토·수정·복사가 끝났을 때 멈춥니다. AI 대기 시간도 포함합니다.

새로고침하기 전에 화면의 **모델명·입력/캐시 입력/출력 토큰·응답 시간**도 따로 기록합니다. 수정한 초안은 새로고침하면 사라집니다. 실제 API 사용 요금이 발생합니다.

## ③ 정답과 대조하고 결과표 채우기

두 작업이 끝난 뒤, 각각 작성한 결과를 아래 정답과 대조합니다. 헤더는 CSV 레코드 1로 셉니다.

| 티켓 | 올바른 판정 | 필요한 근거 |
|---|---|---|
| A | 정상 일치 | CSV 레코드 2 + 시스템 A |
| B | 중복 **및** 이메일 불일치 | CSV 레코드 3·4 + 시스템 B |
| C | 시스템에만 있음 | 시스템 C |
| 새 UUID | CSV에만 있음 | CSV 레코드 5 |

**판정과 근거가 모두 맞아야 해당 티켓을 정답으로 셉니다.** B의 문제 유형 중 하나라도 빠지면 오답입니다. 정확도는 `정답 티켓 수 ÷ 4 × 100`입니다.

헤더를 제외한 행 번호로 기록했다면 헤더 1행을 더해 위 정답과 대조합니다. 같은 행을 가리키는 번호 표기 차이는 오답으로 세지 않고 사용한 기준을 비고에 적습니다. 원본 기록은 그대로 보존합니다.

수정 횟수는 초기 결과를 검토하며 **한 항목의 판정 또는 문구를 고쳐 확정한 것을 1회**로 셉니다. 처음 작성하는 과정의 키 입력은 세지 않습니다. 수정할 필요가 없으면 0회입니다. 확인되지 않은 취소·예약 오류 등을 문구에 추가했다면 별도로 기록합니다.

## 언제 완료인가요?

- [ ] 수동 처리와 비서 사용을 모두 측정함
- [ ] 두 결과를 정답과 대조함
- [ ] 시간·정확도·수정 횟수·AI 사용량·비용 확인 여부를 기록함
- [ ] 측정 조건과 오류·중단 여부를 기록함

결과표와 측정 조건을 전달하면 평가 문서에 정리할 수 있습니다. 키·비밀번호·실제 개인정보는 보내지 않습니다.

**같은 자료를 두 번째 처리하면 기억해서 빨라질 수 있으므로, 이번 1회 비교는 참고 측정입니다.** 시간 절감 효과를 일반화하려면 비슷한 난이도의 다른 명단으로 순서를 바꿔 반복합니다. 자동 테스트 시간이나 AI 응답 시간만으로 사람이 처리한 전체 시간을 대신하지 않습니다.
