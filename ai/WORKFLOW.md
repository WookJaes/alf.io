# 작업 워크플로우

현재 Codex가 필요한 역할을 순차 수행한다. 별도 실행기·로그인·모델 버전 강제 설정은 없다. 작은 수정에는 필요한 단계만 적용하고 모든 문서를 매번 읽지 않는다.

## 진행

1. 요청·완료 기준·변경 범위를 정하고 관련 소스와 지침을 확인한다. [라우팅](routing.md)으로 경로를 선택한다. 이전 실패와 관련이 있을 때 [기억 인덱스](memory/index.md)를 조회한다.
2. 기능 변경·다단계 검증·하네스 변경은 [작업 기록 양식](templates/work.md)으로 docs/harness/records/<날짜>-<작업명>.md를 만든다. 계획·실행 모드·초기 Git 상태를 적고 요청된 변경을 진행한다. 단순 설명·오탈자 수정은 별도 기록을 강제하지 않는다.
3. [로컬 검사](../docs/harness/local-validation.md)에 따라 필수 검증·Review·QA 완료 조건을 선언하고 `init`한다. 자동 검증은 `run`, 수동 검토는 `begin` → 확인 → `record`로 대상 코드·근거를 연결한다. 독립 수행이 필요하면 선언에서 요구하고 실제 보고 주체를 남긴다. 변경에 필요한 테스트·화면·DB 확인만 실행해 명령·종료 코드·실제 건수·증거를 작업 기록에 남긴다. 0건·캐시·미실행을 새 테스트 통과로 표시하지 않는다. 재현이 필요한 검증은 실행 환경·명령 실행 위치·검증 대상 코드·상대경로 증거도 연결한다. 하네스 구조 변경에는 `python3 ai/tests/check.py`와 검사 도구의 회귀 테스트를 실행한다.
4. 실패는 [실패 양식](templates/failure.md)으로 같은 기록에 추가해 환경·구현·도구 문제를 구분한다. 원인과 조치를 바꿔 해결·재검증한다. 권한·필수 정보 부족은 남은 작업과 이유를 알리고 가능한 작업을 계속한다.
5. `gate`를 실행하고 거부된 항목을 보완한다. 실제 diff·완료 기준·검증 증거를 리뷰하고 실행 방식(자체/별도 담당)을 기록한다. 코드·실행 설정이 바뀌면 영향받는 검증과 리뷰를 갱신한다. 전체 완료 기준이 충족돼야 completed, 미검증 조건이 남으면 incomplete로 보고한다.
6. 필요한 사용 문서를 갱신하고 결과·제약·다음 행동을 기록한다. 재사용할 근거 있는 지식만 [기억 양식](templates/memory.md)으로 저장한다. 요청된 작업을 검토 대기만으로 미완료 상태에 두지 않는다. 커밋은 사용자 지시를 따른다.

## 재개

`resume`으로 저장된 결과와 현재 코드·환경·조건을 비교하고 유효하지 않은 단계부터 다시 수행한다. 기록 누락·손상은 복구하거나 새 ID로 선언 후 재실행한다. 같은 조건의 검증은 `reuse`로 출처와 이유를 기록하며 새 실행으로 표시하지 않는다. 이 문서와 검사 도구는 에이전트 실행·상태 전환을 강제하는 런타임이 아니다.


검사 명령은 선언된 결과의 완료 판정만 차단한다. 에이전트의 코드 수정·외부 게시를 강제 제어하지 않는다. 선언의 충분성, 수동 근거의 진실성, 독립 수행 여부와 민감정보 제외는 실제 수행자와 이 워크플로우의 책임이다.
